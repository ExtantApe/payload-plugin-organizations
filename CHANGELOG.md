# Changelog

## Unreleased

> **Check before upgrading: field names in saves, and duplicated records.** Every collection and global in your config, not only the plugin's, refuses a save whose data has a top-level key that isn't a plain field name, such as a dotted one. This applies to server code too, `overrideAccess` included. The refusal is a 400 with a public message, exported as `BAD_KEY_MESSAGE`. If your own code saves a group field as `{ 'group.field': value }`, send `{ group: { field: value } }`. Check your server writes, and your collection and global hooks, for keys like this. Duplicating a record whose organization picker points at a closed, pending or wrong-kind organization, or with access checks on one the person can't read, is refused with the picker's validation error: `That organization isn’t active.` or `That kind of organization isn’t allowed here.` The original still saves.

### Changed

- The field name rule applies to create, update by id, bulk update and duplicate on every collection, and to update on every global, including those that other plugins or Payload add. A save whose data isn't an object is refused the same way.
- A `pendingLevel` sent with a new invitation is dropped.
- The organization picker checks a duplicated record as it checks a new one.
- Tested: typecheck, build and leak check clean, and the 211 tests in this repo pass, full suite run twice, on Payload 3.92.1 and an in-memory MongoDB replica set. The changes in this release are untested by this repo's suite. 13 further tests, not in this repo, passed locally along with it. Not tested: a live site.

## 0.3.0 (2026-11-27)

> **Check before upgrading: your approvers need read access.** Approving, activating a person in a pending organization, closing, reopening, and changing the ROR id or domains are all updates. With access checks on, someone `canApprove` allows now also needs read access to what they update: the organization, or the membership row when they activate a person. Without it they are refused. 0.2.0 didn't ask for read access on any of these, closing included.
>
> Before you upgrade, check that:
>
> - everyone your `canApprove` allows can read those rows. `canRead` gives this. It also opens every organization, membership and history row to them, so check that this is right for each of them.
> - if you replace or wrap the read rule on organizations or memberships, your rule allows them as well. The plugin's rule still has to allow the row, so widening only yours isn't enough.
> - each kind of approver can still approve and close on a test copy of your site, including through any server code that updates as them with `overrideAccess: false`.

### Changed

- Apply read limits to writes. With access checks on, updating an organization or a membership now needs read access to that row, under the plugin's read rule and the one the collection has after your config. A host that lets someone update a row they can't read, or that replaces or wraps a read rule, will see those updates refused unless both rules allow the row. One exception: an invited person whose invitation is hidden from them can send only `status: 'removed'` or only `status: 'active'` (the veto still decides), unless the host replaced the membership read rule. A write to such a row answers with no document (`null`, or `doc: null` over REST), including from server code that passes them as `user`. This replaces what the entry below says about answers to writes on a hidden row.
- Tested: 56 new tests (211 in all; typecheck, build and leak check clean, full suite run twice, once unsharded and once in two shards). 38 cover the read limits on writes over the Local API at depth 0 to 2, REST and GraphQL against Payload 3.92 and an in-memory MongoDB replica set: updates, duplicate and delete, create answers, the exception and its limits, people who may still write, and host read rules that are wider, narrower or failing. 18 cover an approver who isn't staff: without read access they are refused and nothing changes (Local API at depth 0 to 2, REST at depth 0 and 2, and GraphQL), and with it the same person activates a first Coordinator, approves, closes, reopens, sets a ROR id and sets domains over the Local API, REST and GraphQL. All 18 fail on 0.2.0. One existing test now leaves the veto's quiet question out of its expected log. Not tested: join fields, the admin screens, host collections that populate memberships through a write, and a live site.
- An invited person who hasn't accepted now sees the organization, its name and who invited them only when the veto would let them accept. The plugin asks `refuseMember` the question accepting would ask, with `preview: true`, and on a refusal, a throw, any answer but `null` or nothing, or no answer within two seconds, it leaves the invitation row and the organization out of that person's reads and sends any membership row that goes back to them, writes included, without its organization, inviter and remover. They can still decline. A row they accepted at some point shows as before. The veto is still asked for real at accept, nothing changes on the inviter's side, and Coordinators, active members and staff see what they did before. `RefuseArgs` gains an optional `preview: true`. The veto must give the same answer with it and only skip side effects; one that returns early on `preview` shows the details. Hosts whose veto has no side effects change nothing.
- The plugin's collections set `lockDocuments: false`, so Payload keeps no edit-lock rows for organizations, memberships or history. The admin screens no longer warn about two people editing at once; the plugin's own checks still handle two changes at once. The plugin had no option for this before, so no host setting is overridden.
- Tested: 18 new tests (155 in all; typecheck, build and leak check clean, full suite run twice), the read tests failing first against 0.2.0: a refused invitee reads no name or inviter through find and findByID at depth 0 to 2 on both collections and the history, sorting, a nested `organization.name` filter, `select`, a host document populating the organization, REST, GraphQL, counts and the exported helpers; right and wrong guesses in filters count the same; a withdrawn or declined invitation stays hidden; a no-op change, a decline, and a no-op on a declined or withdrawn invitation answer with no name, inviter or organization id over the Local API and REST at depth 0 and 1 and over GraphQL, and the decline still takes effect; accept is still refused with the reason; the picker refuses; an allowed invitee, the inviter, a Coordinator, an active member, staff and a maker of a pending organization see what they did before, writes included, and the veto isn't asked on the inviter's side; a throw, a rejection, `false`, `''`, a reason, `0`, `true`, an object and a veto that never answers all hide; a veto that reads the same collections itself can't loop; the three collections have locks off and the lock collection can't point at them. Not tested: the admin screens in a browser, a live site, MongoDB under load with many invitations per person, how long the inviter's requests take (the inviter's path doesn't call the veto), and GraphQL at a set depth (it follows the fields asked for).

## 0.2.0 (2026-11-24)

### Fixed

- A write refused for a missing transaction (the database stopped handing them out, or server code passed `disableTransaction`) now throws a 403 whose data is exactly `{ refusal: 'transactions-required' }`. The message is unchanged. Review tools such as whitehat count only that shape, or a bare 401, 403 or 404, as a refusal, so this guard showed as not checked before. Tested: 1 new test (137 in all) over the Local API and with `disableTransaction`; it fails on the old code. Not tested: a live site.
- A withdraw and an accept on the same membership at the same moment now end in one success and one plain refusal (403). Before, the one that lost got the database's raw write conflict. Every change to a membership writes the row once to take its lock, as the positions plugin does, and write conflicts (code 112 or `WriteConflict`, also as a nested cause) become the refusal.
- Tested: 5 new tests (131 in all; typecheck and leak check clean, full suite run twice): the conflict matcher, a row held by another open transaction refused with a 403 over the Local API and over REST, and eight rounds of a real withdraw and accept at once on a replica set over each, with no raw error and a final row that is either accepted or withdrawn. The held-row and two-at-once tests fail without the fix. Not tested: a live site, GraphQL for this race, a conflict from a database other than MongoDB, and forcing the two-at-once timing (some rounds run one after the other and both succeed).
- The lock is now taken only after every refusal and the veto have passed, right before the write. Before, it was taken first, so a Coordinator sending harmless changes while a vetoed minor accepted saw "just changed by someone else" and then an unchanged row, which told them the minor was covered by the veto. A refused change now never touches the row, so it also no longer bumps `updatedAt` (seen with `allowWithoutTransactions: true`). The conflict matcher no longer maps a bare `TransientTransactionError` label or a message that only says "write conflict" to that refusal; other faults now show as the faults they are.
- Tested: 5 new tests (136 in all; typecheck and leak check clean, full suite run twice): the matcher refuses the label alone, message-only and wrong-type codes; refused changes (a vetoed accept over the Local API and REST, an unknown level, a bad status, an attempt to change the organization) make no lock write and leave the whole row, `updatedAt` included, unchanged; an allowed change makes one; a Coordinator's no-op change while a vetoed minor accepts gets the same answer as with nothing running, 12 rounds each over the Local API and REST. Four of them fail on the previous code. Not tested: `allowWithoutTransactions: true` itself (the `updatedAt` bump came from the lock write, which the call counts cover), a live site, GraphQL for this race, and a conflict from a database other than MongoDB.

- Every write the plugin guards now refuses cleanly when the database hands back no transaction, or when server code passes `disableTransaction`, and writes nothing. Before, only the start-up check looked, so a database that began answering with no transaction later still let an invitation through. The check runs first in the change hook of organizations, memberships and history rows, with a message saying the change needs a transaction. `allowWithoutTransactions: true` turns it off along with the start-up check.
- A level change that the veto refuses on an active row read the same as any other refused change to the changer; the level-dependent tell this left is fixed by the promotion offer under Breaking.
- Tested: 6 new tests with `beginTransaction` stubbed to answer null after start-up: invite, accept, level change, removal, new organization, edit, close, server-code writes, a history row on its own and `disableTransaction` are refused with no rows or events added, and the same calls work once transactions return (112 tests in all; typecheck and leak check clean). Not tested: a real adapter that loses transactions mid-run, and a live site.

### Breaking

- A promotion of an active member is now an offer. The row keeps its level and gets a new `pendingLevel` field; the person accepts by sending the new level themselves, or declines by sending `pendingLevel: null`. Anyone `canChangeLevel` allows can withdraw it the same way. Before, a Coordinator who promoted someone the host's veto refused got a 403 with no history row, while promoting anyone else worked, which told them who the veto covers (for example a minor). Now the veto runs only when the person accepts, and the promoter sees the same answer, row, history and audit calls for everyone. A demotion still takes effect at once and no longer asks the veto. Two new history events and audit events, `offer-level` and `cancel-level`, record an offer and its withdrawal; `change-level` is recorded when the person accepts. Server code with no signed-in user still promotes at once and sees the veto's reason. Hosts that listed or counted `change-level` events or relied on an immediate promotion need to change.
- `allowWithoutTransactions` must be exactly `true`, `false` or left out. Any other value stops the plugin from starting with an error. Before, it kept the guard on without saying so.
- README and test audit: a wrong level name is fixed (this plugin's levels are Coordinator, Member and Viewer).
- Tested: 14 new tests (126 in all; typecheck and leak check clean, full suite run twice): an adult promotion against a vetoed minor promotion compared field by field from the promoter's side over the Local API, REST and GraphQL (status, body, row, history rows, counts, audit calls); accept, refused accept, decline, withdraw, direct set, demotion and removal clearing an offer; server-code promotion; `allowWithoutTransactions: true` lets writes through; audit hooks silent on a refusal; `disableTransaction` refused on update; the option check. Test databases are stopped and their temp folders removed in a `finally`. Not tested: timing of the promoter's reply (the veto is not called on that path, so no clock test), a live site, the admin screens in a browser, and a person working out from a pending offer that stays pending for a long time.

## 0.1.0 (2026-11-23)

- Three finds in the last-Coordinator check and the invitation duplicate check now pass `pagination: false`, so inside a transaction they don't send a count alongside the find, which can fail intermittently with NoSuchTransaction when it is the transaction's first query. None of them used the total. Tested: a test pins `pagination: false` on every find the plugin makes with a request while its flows run (106 tests; the full suite passed five times in a row). Not tested: a live site.
- The repo, with the standard Payload plugin kit. Public since 2026-11-22.
- The first version of the plugin:
  - `organizations`, `organization-members` and an append-only `organization-events` history. Organizations have a host-defined kind, a status of pending, active or closed, a ROR id, domains and private notes. People join at Coordinator, Member or Viewer.
  - A new organization is always pending, and its first Coordinator is approved by an approver the host names, with no time limit. Nobody approves themselves, and nobody raises their own level. Closing and reopening go through the same gate, and a reopening asks the veto again about everyone in it.
  - Only an approver who didn't make the organization and isn't in it sets a ROR id or domains, and the same holds for approving someone through the membership path, so an approver can't activate their own organization through a second account. The shipped list of public mail, school and internet provider domains can't be put on an organization, and the host can add to it. A university matches people by domain only once it has a ROR id.
  - A last-Coordinator rule: the last active Coordinator can't leave or be demoted, also under two changes at once and from server code.
  - Host hooks `canCreate`, `canPrecreate`, `canUpdate`, `canApprove`, `canInvite`, `canChangeLevel`, `canRemove`, `canSeePrivate` and `canRead`, all failing closed on anything but an exact `true`.
  - A required `refuseMember` veto (a function, or exactly `false`; anything else throws at setup), applied to server code too. It is asked when the person accepts, not when someone else invites them, so an inviter can't tell which accounts it covers. The README warns that its reason is shown and can leak an age.
  - Deletes always throw, even with `overrideAccess`. Hooks get plain ids and the `id` and `data` of the change. A user from another sign-in collection counts as nobody. Names, notes and domain lists have length limits. Private notes are hidden from members.
  - A start-up check that the database can run transactions (opt out with `allowWithoutTransactions`), and a refusal of bulk updates and deletes on the plugin's collections.
  - Domains: public suffixes such as `co.uk` are refused, only added domains are checked on an update, and history rows keep the domain and ROR values and one row per kind of change.
  - Answers an inviter sees are uniform: the veto is not asked on invited rows (level changes on them are refused, reopening checks active people only), an unknown id or an unseen existing row gets the same refusal as any refused invitation, and a person who accepted a place in an organization, or made it, can't approve, reopen or widen it, even after leaving. Closing skips that check.
  - `levelIn`, `organizationsOf`, `organizationField` (which respects the editor's read access), `matchOrganizations` (takes the user, needs a verified email, runs the veto) and the domain helpers.
- Tested: 105 tests against real Payload 3.92 with an in-memory MongoDB replica set: each rule above, refusals over REST, GraphQL and bulk update, server-code attempts to revive or widen a membership, repeated two-at-once runs for the last-Coordinator, duplicate-invitation and unique-ROR rules, the picker, the domain matcher, and clean-up of the database and server at the end.
- Not tested: a database without transactions beyond the start-up refusal (the last-Coordinator guard needs a replica set), a live site, the admin screens in a browser, a very large number of members or domains, and any real ROR data.
